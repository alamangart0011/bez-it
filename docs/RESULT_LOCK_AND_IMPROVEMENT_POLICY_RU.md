# Result lock and improvement policy — room-based V17

## Зачем нужен этот файл

Этот файл фиксирует главный рабочий принцип следующего этапа:

**улучшения разрешены только внутри уже определённого и зафиксированного результата.**

То есть дальше работа идёт не в сторону новых идей, новых продуктовых развилок или нового scope, а только в сторону доведения room-based портала до сильного финального состояния.

---

## Зафиксированный результат

Активный целевой результат уже определён:
- один room-based V17 baseline;
- один active root: `/opt/messenger/contour-chat-jino-final`;
- один active domain: `https://ai.voice.oboron-it.ru`;
- один active continuation branch: `ops/single-contour-cleanup-20260413`;
- один active PR: `#14`;
- room-based модель как единственно верная для продукта.

Это и есть граница результата. Она не обсуждается повторно.

---

## Что считать допустимым улучшением

Допустимое улучшение — это только то изменение, которое:
- усиливает already-fixed room-based результат;
- сокращает путь до live acceptance;
- улучшает shell / dashboard / voice / meeting / admin внутри текущего канона;
- улучшает deploy / runbook / smoke / browser acceptance;
- уменьшает визуальный шум, технический хвост или product drift;
- повышает управляемость active baseline без открытия нового направления.

---

## Что считать недопустимым улучшением

Недопустимо:
- открывать новый product pivot;
- возвращать messenger-first как active interface;
- плодить новые release-ветки или preview-контуры;
- уводить работу в новый большой redesign вне текущего execution sequence;
- менять room-based модель на personal/direct-first модель;
- называть общие размышления «улучшением», если они не сокращают путь до зафиксированного результата.

---

## Приоритет улучшений

### Priority 1
- shell cleanup;
- dashboard dispatcher rewrite;
- voice first-screen compression.

### Priority 2
- meeting cleanup;
- admin cleanup.

### Priority 3
- stabilization;
- release hardening;
- browser acceptance;
- post-launch hardening.

Любое улучшение, которое не попадает в эту очередь, не является текущим обязательным действием.

---

## Принцип принятия улучшения

Перед любым следующим действием задаётся один вопрос:

**это действие приближает уже зафиксированный результат или открывает новый scope?**

Если:
- приближает результат — делать;
- открывает новый scope — не делать сейчас.

---

## Как фиксировать улучшение

После каждого реального полезного улучшения обязательно фиксировать:
- что сделано;
- что дальше;
- какой новый факт подтверждён;
- процент — только если появился новый live/browser/runtime факт.

Фиксация обязательна:
- в чате;
- в docs / PR checkpoint.

---

## Definition of improvement done

Улучшение считается засчитанным только если оно:
- реально изменило code / deploy / runbook / acceptance / UI cleanup слой;
- не вывело проект за границы зафиксированного результата;
- уменьшило расстояние до live acceptance или stabilization;
- отражено в docs / PR.

---

## Финальное правило

Дальше работа идёт по принципу:

**не искать новый лучший продукт, а делать сильнее уже выбранный и зафиксированный результат.**
